# Engine review: what was changed, what was checked, what is left

A code review of the Python engine listed code-health, forecasting-accuracy, scale and feature gaps. Each point was checked against the code. Only the low-risk items were changed before go-live; the rest are planned, with the reason they were not done in a day.

## Changed (2026-11-13)

| Review point | Result |
|---|---|
| All warnings switched off (`warnings.filterwarnings("ignore")`, forecasting.py) | Removed. Each model run is wrapped in `model_warnings(name)`: real fitting trouble (non-convergence, bad values) is logged at WARNING under `wfm.forecast` with the model's name; library deprecation notices go to DEBUG. A repeated message is logged on its 1st, 10th, 100th ... occurrence with a count, so a backtest does not flood the log. |
| `if True:` with odd indentation (scheduling.py `_run_worker`) | Removed; the body is now ordinary 4-space nesting. No behaviour change. |
| State stored on a function (`m_ets.last_mode`) | It was written and never read, so it was deleted. |
| History rebuilt once per forecast day inside a loop (`distribute`) | Built once before the loop. |

Tests: `test_forecast_warnings.py` (5 new). Forecast, SARIMA, engine, bands, walk-forward tests pass. In one full run `test_weekend_shifts_are_spread_over_a_long_period` failed once while the machine was busy (the run took 31 minutes) and passed on its own in 33 s: it is a time-limited solver test, so treat it as load-sensitive, not as a regression from these edits (the edits are syntax-only in scheduling.py).

## Done next: scale, forecast accuracy, email response time (2026-11-13)

**Scale**
- The "starting roster only" label was wrong: it fired on any CP-SAT answer with a gap of 100% or more, even one that beat the starting roster, and then ran HiGHS, SCIP and greedy for nothing. It now compares scores (`_beats_start`). A 355-person build with 12 start times went from 65 s to 35 s as a result.
- Measured limit: 355 people tuned at about 20,000 shift choices and not at about 40,000 (24 start times; 120 s gave the same roster). The Generate checklist now warns above an estimated 45,000 (people x days x start times). One kind of test group only.
- Not done: making the solver cope above that limit (vectorised candidate generation, splitting by team before the limit). Pruning start times automatically was tried on paper and rejected: with 6 start times the tuned roster covered 94.7% against 99.5% for the 12-start starting roster, so pruning would have made it worse.

**Forecast accuracy** (`forecasting.py`, `test_forecast_accuracy.py`, 10 tests)
- Repeating spikes: a spike on the same day of the month, or the last two days of the month, in 2+ different months and the same direction is kept, not cleaned away; a single odd day still is. The gradient-boosted model also gets day-of-month and days-to-month-end as inputs. On a synthetic series with a first-of-month spike, the 30-day error of that model went from 4.1% to 3.4%.
- Long-horizon test: models are also scored on two 4-week walk-forward folds (needs about 140 days of history). Ranking uses the 1-week and 4-week MASE equally when every model has both, otherwise the 1-week figure as before; a model must still beat seasonal naive. The LSTM is only scored at 1 week (too slow to repeat).
- Handle time: a per-day forecast (recent level with a 14-day half-life times a shrunk weekday factor) replaces one average for every day. On a series whose handle time rose 30% the forecast follows the recent level (about 385 s against 345 s for the plain average).
- Not verified: effect on real customer data. These are synthetic tests and the existing walk-forward tests; the new selection rule can pick a different model than before for a given queue, so watch the model choice and accuracy figures after the first refresh. Handle time is not backtested against history.

**Email response-time target** (`staffing.py`, `test_response_time.py`, 8 tests; API test in `backoffice.test.ts`)
- The turnaround field already existed for back office. Email queues now have it too ("Reply within (hours)" in the queue form; 24 = same day, as before). A target under 24 hours staffs each interval for the work that falls due in it: the work that arrives in an interval is spread over the next N OPEN hours, so every message is answered inside N open hours. A test serves random arrivals with the resulting staffing and checks every message is answered in time for targets of 1, 2, 4 and 8 hours; tighter targets never need fewer people.
- Targets count opening hours, not clock hours; mail arriving while closed waits for the next opening; a daily total with no time of day is assumed to arrive evenly over the opening hours; work still due after the last forecast day is left to the days after it. Back office uses the same rule below 24 hours; above 24 it behaves as before.
- Existing email queues with no value, or 24, behave exactly as before. A queue that already had a turnaround set through the API (it was ignored for email) will now use it.
- Not built: a reply-within target by percentage (for example "90% within 4 hours"); the rule staffs for all of it.

Tests run: 149 engine tests (forecast, staffing, backends, server) passed, plus parity, scheduling and LSTM (107) earlier; gateway unit tests (22) and the API test for email; Generate browser check 28/28.

## Third review round (2026-11-14)

- **Bands beyond a week.** The band edges came only from the 7-day backtest, and beyond a week a fixed formula (square root of 1 + days/28) widened them: a guess, never calibrated or tested. The 4-week backtest now keeps its per-day errors for days 8 to 28 (`backtest_long`), and `calibrate_far` turns them into band edges for those days, with held-out coverage tested leave-one-fold-out like the 1-week band. Up to a week nothing changes; 8 to 28 days uses the measured edges; beyond 28 days they widen from where they were measured. A far band is never narrower than the old rule gave, so a lucky 4-week test cannot tighten it. The 15-minute bands use the same curve (`Sigma`, `sigma_at`). A queue with under about 140 days of history says in its notes that the far band is not calibrated; one whose held-out coverage is poor says to treat it as optimistic; the calibration (points, edges, coverage) is recorded in the forecast's `model_config`. Tested on synthetic errors with a known spread (coverage near 10% and 90%) and through `forecast_queue`. **Not verified on real data**: the reviewer's figure of 59% at or under P10 at 8 weeks was not reproduced here, and only two 4-week folds feed the calibration, so it is a noisy estimate that improves with history.
- **Starting-roster wording.** The report, the Generate checklist and the Solver tile no longer say "not tuned to the forecast": they say the optimiser found nothing better than the starting roster in the time given and that it may already be close to the best.
- **Repeated log lines.** A model that cannot be fitted is now logged once per model (the first error), through the same counted path as other fit warnings (1st, 10th, 100th occurrence), not once per backtest fold.
- **LNS on real data: still open.** On the synthetic 200-agent week there is almost nothing to gain, so it cannot show the effect. It needs the real 355-person week (about 55,000 candidate shifts) built with and without `ENGINE_LNS_BELOW_WORKERS=0` on a 2-core server, comparing the score. The change cannot return less than the start, but its gain is unproven.

Still not done from the review: one rule list for both solvers, splitting `scheduling.py`, reformatting long lines.

## Fourth review round (2026-11-14): the yearly pattern, and two text fixes

- **Advice text.** `backends.advise()` no longer says the starting roster is "not tuned to the forecast". For the starting roster it now says the solvers found nothing better in the time given and it may already be close to the best; for a backup solver's roster it says CP-SAT's, had it finished, could be better. (The report, checklist and Solver tile were changed earlier.)
- **Doc contradiction.** Fixed above (the email target and the withdrawn breaks point).
- **Yearly pattern: only the gradient-boosted model could see it.** Holt-Winters, ARIMA and SARIMA are weekly only, Holt-Winters also looks back at most 280 days, and nothing used the same weeks last year. Now, with about 13 months of history or more, the forecast of the chosen model is pulled toward how the same weeks moved last year: `ratio(d) = A(d - 364 days) / A(end - 364 days)`, A being the centred 28-day mean (`annual_ratio`); the forecast is multiplied by `1 + w (ratio - 1)`. The weight w (0.25 to 1) is chosen on a walk-forward test of the chosen model from up to 8 origins four weeks apart across the past year or so (`annual_backtest`, `choose_annual_weight`), and is used only if it cuts the 4-week error by at least 3% and there are at least 3 origins; otherwise nothing changes. The notes say how far it was pulled and the gain; the weight and gain are in the forecast's `model_config`. The far-ahead band is now calibrated on the same year-spread folds when there are enough (more than the two folds of the 4-week test), on the adjusted forecast.
- **Why not Fourier terms in Holt-Winters.** Holt-Winters in statsmodels takes no regressors. The ratio gives every model the yearly shape and is checked in a backtest before use, so I did not add Fourier terms to ARIMA as well: that would double the effect and the risk. Revisit if the backtest shows ARIMA leaving yearly error on the table.
- **A finding on the way.** The history cleaner replaces days that stand out from their weekday's baseline, and a multi-week swing larger than about 30% (a deep August lull, a December rush) can be cleaned away as outliers, taking the yearly shape with it. So last year's movement is read from the history as it happened (known events replaced), not from the cleaned one, and the yearly test is scored against the same. The cleaner itself is unchanged: seasonal swings above that size are still partly cleaned out of what the models train on.
- **Tests** (`test_forecast_accuracy.py`, 28 tests in the file): the ratio equals the true seasonal movement within 6%; none under about 13 months of history; the weight is full when last year explains the error and zero when it is noise; on a series with a summer lull and a December rush the 4-week error fell from the no-adjustment figure to under 75% of it, the weight and gain are recorded; a smooth cycle that Holt-Winters already tracks is left alone (weight 0). 44 engine tests in the band, warning and enforcement files also pass.
- **Not verified on real data.** All of this is on synthetic series. Real yearly patterns are noisier, a one-off last year (an outage, a campaign that was not entered as an event) in the same weeks leaks into the ratio (damped by the 28-day average, the ratio limit of 0.5 to 2, and the weight having to prove itself), and the 3% minimum gain is a judgement, not a measured value. Expect the first refresh on a customer with 2 or more years to change some forecasts: check the notes for "pulled ... toward how the same weeks moved last year".

## Checked, and different from the review

- **Breaks are optimised.** A real build records `breaks: {shiftsChanged, phoneShortfallBefore, phoneShortfallAfter}` (`breakOptimizer.ts`), and an intraday gap fixer exists (`gapFixer.ts`, `intradayGapRoutes.ts`). What is missing is re-optimising the rest of the day from live adherence: that part of the review stands.
- **Email workload is modelled** (staffing.py spreads email/back-office work over working hours). The email response-time target the review found missing has since been built (see "Done next" above: "Reply within (hours)" on email and back-office queues).
- The duplicated model is guarded by `test_backend_parity.py`, which compares the LP and CP-SAT answers. That reduces the risk; it does not remove the double maintenance.

## Not done, and why (updated: items 4, 5 and the email target of 6 are now done in part; see the section above)

These change how schedules or forecasts are produced. Each needs its own design, test data and a before/after comparison, which cannot be done safely the day before go-live.

1. **One rule list for both solvers** (`build_lp` in backends.py and the CP-SAT model in scheduling.py). Plan: a neutral list of rules (weekly hours, rest, days per week, consistency, coverage with over/under) that each backend translates; parity test kept as the safety net; migrate one rule family at a time.
2. **Split scheduling.py (1,258 lines)** into about four modules: memory and workers, starting roster, CP-SAT model, multi-week driver. Pure moves, but worker processes load these by name and pickle across them, so every entry point and every test that imports them needs checking.
3. **Very long lines.** Run a formatter once, in a commit of its own, so it does not hide real changes in review.
4. **Forecast accuracy:** (a) repeating spikes are cleaned away as outliers: keep days that recur on the same date or weekday pattern; (b) the backtest looks one week ahead: score at the horizons the schedule uses (1, 4, 13 weeks); (c) no real handle-time forecast: model AHT per interval and per queue instead of the profile average. Each is measured against the current walk-forward results before it replaces anything.
5. **Scale:** pure-Python loops, the 300,000-candidate limit and one search thread are real limits (see the 355-person experiment in GENERATE_SCHEDULE.md: many shift templates leave the optimiser on its starting roster whatever the time). Plan: vectorise candidate generation, split by team before the limit is hit, and measure how many templates a given crew size can carry.
6. **Features:** long-term capacity planning beyond the Staffing screen and live re-optimising during the day. (Email response-time targets: done, see above.) The reviewer also withdrew the point that breaks are not optimised: they are, in the gateway (`breakOptimizer.ts`); the review had looked at the engine only.
